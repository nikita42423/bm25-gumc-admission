# Задачи: Тошниёзов Жавохирбек — «Корпус и benchmark»

## О проекте за 1 минуту
«Помощник абитуриента ГУИМЦ» — сайт-чат для абитуриентов с нарушениями слуха и их родителей.
Пользователь пишет вопрос → сервер ищет подходящие фрагменты в документах приёмной комиссии
(поиск BM25) → LLM пишет короткий ответ → пользователь видит ответ и источник.

Твоя зона — **данные**: документы, по которым идёт поиск (корпус), и тестовые вопросы,
по которым мы проверяем качество поиска (benchmark). Программировать не нужно.

## Что можно менять
Только эти файлы и папки:
- `data/` — скачанные документы и список источников
- `benchmark/` — тестовые вопросы
- `spec/tech/rag.md` — только раздел «1. Корпус»

Всё остальное **не трогать**. Правила работы с git — в [docs/team.md](../team.md).

## Термины (выучить — спросят на защите)
- **Корпус** — все документы, в которых ищем ответ.
- **Фрагмент** — кусок документа (обычно пункт правил), который находит поиск и показывает пользователю.
- **BM25** — формула, которая оценивает, насколько фрагмент подходит к вопросу: учитывает, сколько раз
  в нём встречаются слова вопроса и насколько эти слова редкие.
- **Benchmark** — набор тестовых вопросов, для которых заранее известно, какие фрагменты правильные.
- **Recall@5** — какая доля правильных фрагментов попала в первые 5 результатов поиска (от 0 до 1, больше — лучше).
- **MRR** — насколько высоко стоит первый правильный фрагмент: на 1-м месте = 1, на 2-м = 0.5, на 3-м = 0.33…

Для **каждого** вопроса открой ожидаемый документ (колонка «Где ожидаем ответ»), найди пункты,

## Этап 2 (ноябрь): Ж4 и Ж5
Ж1–Ж3 приняты. Капитан перенёс твою разметку в `benchmark/queries.json` — теперь у каждого
вопроса есть id фрагментов (например, `rules_2_8` = Правила, п. 2.8). Поиск и LLM работают.

Новые термины:
- **Эталон** — правильный ответ на вопрос, написанный человеком по документу.
- **Вопрос-ловушка** — вопрос по теме поступления, ответа на который в документах **нет**.
  Система должна честно сказать «В документах нет этой информации.», а не выдумать.
- **Accuracy** — доля правильных ответов системы на обычные вопросы.
- **Correct Rejection Rate (CRR)** — доля ловушек, на которые система правильно отказалась отвечать.

### Ж4. Эталоны и вопросы-ловушки (файл `benchmark/queries.json`)
1. Для **каждого** из 27 вопросов заполни поле `"reference"`: правильный ответ в 1–3 предложениях,
   своими словами, **только по пунктам из `"relevant"`**. Числа, сроки и названия — точно как в документе.
   ```json
   "reference": "Нужны заявление, паспорт, документ об образовании и фотографии (Правила, п. 2.8)."
   ```
2. Добавь в конец файла **5 вопросов-ловушек** (Q28–Q32). Перед тем как добавить, проверь
   поиском по PDF (Ctrl+F), что ответа в документах действительно нет. Примеры тем: стоимость
   обучения на платном, расписание занятий, есть ли в общежитии Wi-Fi, адрес столовой.
   ```json
   {"id": "Q28", "type": "trap", "question": "…", "relevant": [], "reference": "В документах нет этой информации."}
   ```
3. Проверь, что файл не сломан: `python benchmark/run.py` должен напечатать Recall@5 без ошибки.

### Ж5. Проверка ответов системы (после того как капитан запустит `--answers`)
1. Открой `benchmark/results.md`, раздел «Ответы по вопросам», и сравни каждый ответ с эталоном.
2. Создай `benchmark/answer_review.csv`:
   ```
   id,correct,comment
   Q01,1,
   Q02,0,перепутан срок: в документе 25 июля
   ```
   `1` — ответ верный и ничего не выдумано, `0` — есть ошибка или ответ неполный.
3. Снова запусти `python benchmark/run.py --answers` — в `results.md` появится Accuracy.
4. Допиши в `benchmark/report.md` раздел «Анализ ошибок»: 3–5 примеров неверных ответов
   и почему так вышло (поиск не нашёл нужный пункт / LLM неправильно поняла фрагмент).

Подготовить 2–3 слайда для защиты: корпус, примеры вопросов, Recall@5, MRR, Accuracy, CRR.

**Готово, когда:** у всех 27 вопросов заполнен `"reference"`, есть 5 ловушек, `run.py` работает,
изменены только файлы в `benchmark/`. Ветка `javohirbek/answers` → Pull Request.
