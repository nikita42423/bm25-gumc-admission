# RAG: поиск BM25 и ответ LLM

Ответственные (зона «BM25 и RAG»): корпус и benchmark — Тошниёзов Ж. Г.;
предобработка, индекс, BM25 и LLM — Кузнецов Н. В.

Схема: **вопрос → предобработка → поиск BM25 по индексу → top-5 фрагментов → LLM → ответ + источники.**

Источник: https://bmstu.ru/documents — «Документы, регулирующие положение приёмной комиссии».

PDF скачиваются в `data/raw/`, извлечённый текст — в `data/corpus/`. Название и ссылка на PDF
каждого документа — в `data/sources.csv` (`file,title,url`); они показываются пользователю как источник.

## 2. Документ (единица индекса)
Документ корпуса — **фрагмент**. Корпус собирает `python scripts/build_corpus.py`
(PDF → `data/corpus/fragments.jsonl`, сейчас **491 фрагмент**).

- Текст из PDF — библиотекой `pymupdf`. Колонтитулы, номера страниц и подписи удаляются.
- **Пункт** («2.8. …», «II. 1. …», «Приложение А, п. 2») — один фрагмент. Новый пункт
  принимается, только если его номер — правдоподобное продолжение предыдущего
  (2.8 → 2.9, 2.8 → 3.1, 2.8 → 2.8.1). Так числа внутри текста («до 25.07.») не режут пункт.
- **Длинный пункт** режется на окна по 150 слов с перекрытием 30 слов:
  `rules_2_8`, `rules_2_8__2`, …
- **Таблицы** (баллы, перечни направлений, расписание) — окна по 150 слов текста страницы: `app01_t14`.
- id = код документа + номер пункта: `rules_2_8`, `app11_A_2`, `schedule_II_1`, `app06_note_2`.

Почему так: пункт правил — законченная мысль, его удобно показать как источник и передать LLM.
Целый PDF слишком велик, отдельное предложение теряет контекст.

Поля фрагмента: `id`, `doc`, `title` (название документа), `point` (например, «п. 2.8»),
`page`, `url` (ссылка на PDF), `text`.

## 3. Предобработка
Одинаковая для фрагментов и для вопросов (`app/search/preprocess.py`).

1. Нижний регистр, `ё` → `е`.
2. **Токенизация** регулярным выражением `[а-яa-z0-9]+`: токен — слово или число.
   Числа сохраняем: в вопросах бывают даты, баллы, номера пунктов.
3. **Лемматизация** библиотекой `pymorphy3`: «документов», «документами» → «документ».
   Обоснование: русский язык сильно изменяется по падежам и числам; без лемматизации
   вопрос «какие документы» не найдёт фрагмент «перечень документов».
   Готовая библиотека лемматизации методичкой разрешена.
4. **Стоп-слова** (предлоги, союзы, частицы: «и», «в», «на», «для», «ли» …) удаляем —
   они есть почти в каждом фрагменте и не помогают ранжированию.

Ещё два улучшения (каждое проверено на benchmark, см. раздел 6):
- **Название документа в индексе.** К тексту фрагмента при индексации добавляется название
  документа («Приложение 11. … для лиц с ОВЗ. …»). Пункт «5. …» сам по себе не говорит,
  что он про ОВЗ, а название — говорит.
- **Синонимы в вопросе** (`app/search/synonyms.py`). Абитуриент пишет своими словами,
  документ — официальными: «экзамен» → «вступительное испытание», «оспорить» → «апелляция»,
  «из дома» → «дистанционный», «слабослышащий» → «ОВЗ, инвалид». К леммам вопроса
  добавляются леммы синонимов; фрагменты не меняются.

## 4. Индекс и BM25
Индекс и BM25 написаны **сами** (`app/search/bm25.py`, готовые поисковые библиотеки не используются).

- Обратный индекс: `терм → {id фрагмента: TF}`.
- Храним: `DF(t)`, длину каждого фрагмента `|d|`, среднюю длину `avgdl`, число фрагментов `N`.
- IDF(t) = ln(1 + (N − DF(t) + 0.5) / (DF(t) + 0.5))
- BM25(q, d) = Σ<sub>t∈q</sub> IDF(t) · TF(t,d)·(k1 + 1) / (TF(t,d) + k1·(1 − b + b·|d|/avgdl))
- Каждый терм вопроса считается один раз.
- **k1 = 1.5, b = 0.75** — подобраны на benchmark (сетка k1 ∈ {1.2; 1.5; 2.0}, b ∈ {0.5; 0.75; 0.9};
  разница в пределах ±0.02, оставили стандартные значения).
- Возвращаем **top-5** по убыванию BM25; при равенстве — по id.
- Проверка формулы — тест на примере из занятия 3 (`tests/test_bm25.py`: 0.940 / 0.470 / 0.470).

Индекс строится в памяти при старте сервера (менее секунды на 491 фрагмент), отдельный файл не нужен.

**Порог «ответа нет».** Если лучший фрагмент набрал BM25 < **5.0**, LLM не вызывается, ответ —
«В документах нет этой информации.» (сценарий С3). Порог низкий намеренно: короткий правильный
вопрос набирает ~7.5, а вопросы совсем не по теме (погода, метро) — меньше 5 или ничего.
Пограничные вопросы (Wi-Fi, деканат ИУ5) отсекает LLM по промпту.

## 5. Генерация ответа (LLM)
Модель — **YandexGPT** (`yandexgpt/latest`) через API Yandex Cloud (`app/llm.py`).
Почему: хорошо понимает русский, доступна из России, работает на любом компьютере (локальная
модель на нашей видеокарте 4 ГБ не запустилась), для учебного объёма хватает стартового гранта.
Доступ — API-ключ сервисного аккаунта с ролью `ai.languageModels.user`; ключ и id каталога —
только в `.env` (`YANDEX_API_KEY`, `YANDEX_FOLDER_ID`, пример — `.env.example`), в Git не попадают.
Параметры: temperature 0.1 (меньше фантазии), до 600 токенов ответа.

Код вызова изолирован в одном модуле, провайдер переключается в `.env`:
`LLM_PROVIDER=ollama` — локальная Qwen 3.5 (4B) через Ollama (запасной вариант, пока не настроен).

Промпт (`app/rag.py`):

```
[system]
Ты помощник приёмной комиссии МГТУ им. Н. Э. Баумана. Тебе пишут абитуриенты
с нарушениями слуха и их родители.
Отвечай ТОЛЬКО по фрагментам документов из сообщения пользователя. Не используй другие знания.
Пиши по-русски, коротко (2–5 предложений), простыми словами.
После каждого утверждения укажи номер фрагмента в квадратных скобках, например [2].
Если во фрагментах нет ответа на вопрос, ответь ровно одной фразой: «В документах нет этой информации.»
Не придумывай сроки, баллы, адреса и названия документов.

[user]
Фрагменты документов:
[1] <документ>, <пункт>:
<текст>
...
Вопрос: <вопрос пользователя>
```

Источники: пользователю показываются фрагменты, номера которых LLM процитировала ([1], [3]);
если LLM ничего не процитировала — все top-5. Ответ без источника не показываем.

- LLM ответила «нет этой информации» → `answer` = эта фраза, `sources` пустой.
- LLM недоступна (нет ключа, нет сети, ошибка API) → `answer` = «Не удалось сформировать ответ…»,
  `sources` = top-5 фрагментов: пользователь всё равно видит, где искать.

## 6. Оценка качества
Вопросы — [benchmark/queries.json](../../benchmark/queries.json) (из `queries.md`; разметка — Тошниёзов Ж.).
Запуск: `python benchmark/run.py [--compare] [--answers]` → `benchmark/results.md`.

**Поиск** (обычные вопросы):
- **Recall@5** — доля релевантных пунктов, попавших в top-5, в среднем по вопросам.
  Пункт считается найденным, если в top-5 есть любой его фрагмент.
- **MRR@5** — среднее 1 / (позиция первого релевантного фрагмента), 0 если его нет в top-5.
- **Потолок Recall@5** — максимум при идеальном поиске: у многих вопросов больше 5 релевантных
  пунктов, а мест в выдаче 5. Сейчас потолок 0.93.

**Ответы** (`--answers`, нужен ключ LLM в `.env`):
- **Accuracy** — доля правильных ответов на обычные вопросы; правильность размечается вручную
  в `benchmark/answer_review.csv` (сравнение с эталоном из `queries.json`).
- **Correct Rejection Rate** — доля вопросов-ловушек (ответа в документах нет),
  на которые система честно ответила «нет информации».
- Ложные отказы — сколько обычных вопросов получили «нет информации».

Сравнение вариантов поиска (по одному улучшению) — в `benchmark/results.md`.

Ограничение: синонимы составлены, глядя на вопросы benchmark, поэтому Recall на них может быть
завышен. Новые вопросы-ловушки и эталоны (задача Ж4) частично проверяют систему на «чужих» вопросах.
